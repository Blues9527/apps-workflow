# 创意主题、竞品与 PRD

目标：基于用户提供的目标 App 收敛「二创/优化」方向，再写出一份开发能实现、测试能验收、设计能落地、P0 能被 5 图锁定的 PRD。

## 输入

- `artifacts/01-feature-spec/` 全部文件
- `artifacts/00-intake.md`：目标 App、目标市场、平台、时间、团队
- 目标 App 的公开截图/录屏：用于保持品类与核心闭环
- 商业目标：订阅、广告、交易、留存、品牌
- 约束：预算、合规、已有技术栈、不可变范围
- 数据策略：MVP 默认本地 mock，不接真实 API

## Codex + spec-manager 模式（默认）

本阶段由 **Codex** 执行，产出写入 spec-manager **L1**；人类确认后 OpenCode 才能进入阶段 3。

开始前：

```bash
spec-manager brief "<二创主题 + 竞品 + PRD>" --topic <topic>
spec-manager spec list --topic <topic>
spec-manager decision list --topic <topic>
```

创建 L1：

```bash
spec-manager spec new L1 --topic <topic> --title "<产品名> PRD"
spec-manager template L1 --title "<产品名> PRD" --output .spec-manager/drafts/<topic>-L1.md
# 填写主题候选、评分、竞品矩阵、PRD、P0 5 屏草案、mock 数据、验收标准
spec-manager spec update <L1> --content .spec-manager/drafts/<topic>-L1.md   --ai-summary "<一句话摘要>" --change-summary "initial L1 PRD"
spec-manager spec validate <L1>
```

硬规则：

- L1 创建后保持 `draft`，Codex 不得自己 `approve`。
- L1 未 confirmed 不写 L2；Codex 不写实现代码。
- 人类确认后执行 `spec-manager approve <L1>`。
- 若 Codex 不可用，自动由 OpenCode 按同一流程创建 L1，并标记 `codex fallback`。

## PRD Intake 模式（`--prd` / `--prd-spec`）

当用户提供已有 PRD 时，不重新生成主题/竞品/PRD；把 PRD 规范化为 L1。

### 输入

- `--prd <path|url>`：Markdown/文本/可抓取 URL
- `--prd-spec <L1-code>`：已有 spec-manager L1
- PDF/DOCX：先要求用户导出 Markdown，不猜测内容

### 流程

1. 复制原始 PRD 到 `artifacts/02-prd/source-prd.md`，记录来源、日期、SHA256。
2. 写 `artifacts/02-prd/prd-intake.md`：
   - 已有章节/缺失章节/冲突
   - 需求 ID 映射（保留原 ID；没有则生成 `R-xxx`）
   - P0 5 屏分配草案（PRD 有则保留，没有则标 gap）
   - 假设与待确认项
3. 创建 L1，把 PRD 内容填入 L1 模板；保留原始措辞、范围与 ID，不擅自改写。
4. 缺失章节/冲突只向用户确认或标 gap；不做无依据补写。
5. `spec-manager spec validate <L1>`；停止等待人工确认。
6. `--prd-spec` 已 confirmed：跳过创建，直接进阶段 3；draft：先 review/confirm。
7. 人工确认后 `spec-manager approve <L1>`；导出 `02-prd/` 阅读副本。

### 硬规则

- 不覆盖原始 PRD。
- 不把 PRD 没写的功能/范围写进 P0。
- PRD 与目标 App 冲突时，以 PRD 为准并记录 decision。
- PRD 起点下，阶段 1 可 skipped；不要伪造功能清单。

## 流程

### 第 1 步：生成创意主题

基于功能知识库，生成 3-5 个**基于目标 App 的二创/优化**主题。每个主题写：

| 字段 | 内容 |
| --- | --- |
| 主题 ID | T-01 |
| 目标 App 参照 | 保留哪个品类、核心闭环、关键页面 |
| 一句话定位 | 在目标 App 基础上优化什么，和原版/竞品有什么不同 |
| 目标用户 | 具体人群与场景，不写「所有人」 |
| 核心差异 | 1-2 个可被功能验证的差异点 |
| 视觉关键词 | 3-5 个，供阶段 3 使用 |
| 变现假设 | 订阅/交易/广告/暂无 |
| 主要风险 | 获客、合规、技术、内容供给 |
| MVP 适配 | 首版能否在时间内做完 |

硬规则：

- 主题必须与目标 App **同品类、同核心闭环**，属于二创或优化，不是转向另一个产品。
- 例如目标 App 是「剧集资料/发现」，候选主题不能变成「纯壁纸 App」「社交社区」或「流媒体播放器」。
- 差异点可以是体验、信息架构、内容组织、跨平台、商业化，但不能改变用户来这个 App 完成的 core job。
- 偏离品类的候选直接淘汰，不进入评分。
- 主题不是「换皮」：不能只改颜色和名字；差异点要能落到需求 ID。

### 第 2 步：主题评分与收敛

用加权矩阵，1-5 分：

| 维度 | 权重 | 说明 |
| --- | --- | --- |
| 用户价值 | 20% | 是否解决目标用户真实问题 |
| 差异化 | 20% | 相对目标 App 与竞品的改进 |
| 目标一致性 | 20% | 同品类、同核心闭环、能复用目标 App 的心智 |
| MVP 可行性 | 20% | 5 图 + mock 数据 + 单端能否按时完成 |
| 变现潜力 | 10% | 后续联盟/广告/合作 |
| 品牌/视觉延展 | 10% | 是否能形成一致的设计语言 |

输出 1 个主主题 + 1 个备选，写清选择理由和放弃理由。主主题进入 PRD。目标一致性低于 4 分的主题不得作为主主题。

### 第 3 步：竞品研究

选 5-8 个：

- 直接竞品：解决同一问题、同一人群
- 相邻产品：解决相邻问题，可能吞掉你的场景
- 替代方案：用户现在用什么凑合（表格、社群、线下）

每个竞品记录：

| 字段 | 内容 |
| --- | --- |
| 名称/平台/版本 | 可核验 |
| 定位与目标用户 | 商店文案 + 实际体验 |
| 首次启动与引导 | 几步、要什么权限、是否强制登录 |
| 核心循环 | 触发 → 行动 → 奖励 → 投入 |
| 变现 | 订阅、买断、消耗品、广告、抽成 |
| 留存机制 | 推送、签到、内容更新、社交 |
| UI 模式 | 导航、卡片、空态、付费墙 |
| 评论痛点 | 只引用公开评论，标注来源与日期 |
| 可借鉴 | 模式，不抄资产 |
| 机会点 | 你能做得更好的地方 |

规则：

- 每个结论带来源 URL 与访问日期。
- 不编造 DAU、收入、下载量、排名；拿不到就写「未获取」。
- 不把竞品的功能直接等价为「用户需要」；要写你的判断依据。
- 引用评论时保留原文语境，不拼接、不歪曲。

### 第 4 步：定位与范围

在 PRD 开头写清：

- 产品一句话（明确「基于目标 App 的二创/优化」）
- 目标用户与非目标用户
- 首版要解决的 3 个问题
- P0 的 5 屏分配草案：哪 5 屏、每屏承接哪些 P0 需求
- 明确不做的功能（5 图外默认不做）
- 成功指标（可测量，例如「首周完成核心任务 ≥ 40%」）
- 依赖与约束
- 数据策略：本地 mock + Repository 接口，真实 API 不作为 P0 依赖

### 第 5 步：写 PRD

`prd.md` 至少包含：

1. 背景与目标（与目标 App 的关系）
2. 用户与场景
3. 范围（In / Out）
4. 信息架构与导航
5. 5 屏 P0 分配草案（阶段 3 锁定）
6. 功能需求（按模块）
7. 非功能需求
8. 数据与埋点（MVP 使用本地 mock）
9. 权限与隐私
10. 异常与边缘情况
11. 国际化与可访问性
12. 依赖与风险
13. 发布标准
14. 待确认问题

功能需求写法：

```markdown
### R-012 保存草稿

- 关联功能: F-008
- 优先级: P0
- 描述: 用户在编辑页返回或切后台时，自动保存当前内容为草稿。
- 验收标准:
  - Given 用户已输入至少 1 个字符
  - When 用户点击返回或 App 进入后台
  - Then 内容写入本地草稿，并在下次进入编辑页时恢复
- 异常:
  - 存储失败时提示「草稿保存失败」，不丢失当前输入
- 埋点: draft_save_success / draft_save_failed
```

要求：

- 需求 ID 唯一，格式 `R-xxx`；关联功能 ID `F-xxx`。
- 每条 P0/P1 需求必须有 Given/When/Then 验收标准。
- 每条 P0 必须标注落在 5 屏中的哪一屏；放不进 5 屏的需求降为 P1/P2。
- 验收标准必须可观察、可测试，不写「体验流畅」这类无法验证的描述。
- 非功能需求必须带指标：启动时间、崩溃率、包体积、离线能力、最低系统版本；mock 阶段不承诺真实 API 延迟。
- 埋点事件名、触发时机、参数一次定义，后续开发测试共用。
- 权限逐项说明用途、拒绝后的降级路径。
- 数据需求写清 mock 数据结构、Repository 接口、失败/空/离线模拟方式。
- 边缘情况覆盖：空数据、超长文本、弱网、离线、重复提交、权限拒绝、内容下架。

### 第 6 步：自洽审计

逐项检查并记录在 `decisions.md`：

- **目标一致性**：主题与目标 App 同品类、同核心闭环，属于二创/优化而非转向。
- **双向追溯**：每个 P0/P1 功能都有需求；每条需求都能回到功能或商业目标。
- **P0 ↔ 5 屏**：每条 P0 都有目标屏幕；5 屏之外没有 P0。
- **术语一致**：同一概念只用一种叫法。
- **优先级一致**：P0 之间无资源冲突；范围外的功能没有被写成 P0。
- **权限最小化**：没有「先要权限再说」的无关权限。
- **变现与体验**：付费墙不阻断核心闭环，或明确说明阻断策略；首版可不变现。
- **异常闭环**：每条主路径都有失败/取消/重试。
- **指标可测**：成功指标有口径、数据源、时间窗。
- **文案可证**：PRD 里的功能声明都能在 UI 或行为中验证。
- **Mock 可行**：P0 不依赖真实 API；mock 数据能覆盖成功/空/错误/离线。
- **依赖可行**：第三方 SDK、资质、内容供给有负责人和时间。

### 第 7 步：人工签核

向产品负责人展示：

- 主主题与备选、评分
- 竞品差异与机会
- P0 范围与明确不做的事
- 关键假设、风险、待确认问题
- 首版成功指标

获得明确「通过」后，G2 才算完成。

## 产出

```text
specs/<topic>/<topic>-L1.md     # 源（spec-manager）
artifacts/02-prd/
├── theme.md
├── competitors.md
├── prd.md
└── decisions.md                # 阅读副本 + 人工签核记录
```

`L1` 是源；`02-prd/` 是从 L1 导出的可读副本，二者内容必须一致。`decisions.md` 记录：主题选择、范围取舍、竞品启发、需求变更、人工签核结论。

## G2 门禁

- [ ] L1 已创建并通过 `spec-manager spec validate`
- [ ] 3-5 个主题均为目标 App 的二创/优化，且目标一致性 ≥ 4 分
- [ ] 5-8 个竞品有来源、日期、可核验信息
- [ ] 无编造的下载量、收入、排名、评论
- [ ] 每个 P0/P1 功能都有需求 ID
- [ ] 每条 P0/P1 需求有可测试的验收标准
- [ ] 每条 P0 都有 5 屏分配草案，5 屏外无 P0
- [ ] 数据源为本地 mock，Repository 接口已定义
- [ ] 功能 ↔ 需求双向追溯完整
- [ ] 范围外清单明确
- [ ] 非功能需求有数字指标
- [ ] 埋点、权限、隐私、异常路径已定义
- [ ] 自洽审计无未解释冲突
- [ ] intake 模式：`source-prd.md`、SHA256、`prd-intake.md` 已保存；未改写原始范围；需求 ID 映射完整
- [ ] 人类明确确认 L1，且 `spec-manager approve <L1>` 已执行
- [ ] L1 code 已写入 `workflow-state.md`

## OpenSpec 映射（可选）

项目已采用 OpenSpec 时：

- `theme.md`、`competitors.md` 作为 `proposal.md` 的背景与依据
- `prd.md` 的需求转为 `specs/<capability>/spec.md` 的 Requirement + Scenario
- 实现任务写入 `tasks.md`
- 决策写入 `design.md` 或 `decisions.md`

未安装 OpenSpec 时不要伪造目录或命令。

## 常见错误

- 主题偏离目标 App：把「优化」做成另一个品类
- P0 写成愿望清单：5 屏放不下还硬塞
- 把真实 API/后端写成 P0 依赖，导致无法用 mock 交付
- 先写功能列表再补「差异化」：主题变成装饰
- 竞品只抄功能，不分析为什么有效
- PRD 写成愿望清单：没有验收标准、没有异常路径
- 需求 ID 和功能 ID 脱节：测试无法追溯
- 把「提升体验」当成功指标
- 付费墙挡住 P0 闭环却不在范围里说明
- 用未经验证的数据支撑定位
