# 功能分析与知识库

目标：产出一份完整、可追溯、可交接的功能知识库。读者是后续的 PRD、设计和开发 Agent，他们不应该需要再打开原 App 才能理解功能。

## 输入

必需：

- App 名称、平台、版本号、来源链接或安装包（**一个平台即可**）
- 可运行的设备/模拟器，或足够的截图与录屏
- 分析范围（全量 / 指定模块 / 只做核心闭环）

可选：

- 商店截图、隐私标签、帮助中心、更新日志
- 公开评论、教程、媒体报道
- 页面结构导出、网络请求记录（仅限你有权分析的 App）

## 合规边界

只分析公开可观察的行为与界面。禁止：

- 绕过登录、付费墙、订阅、DRM、反调试
- 抓取非公开接口、用户数据、私有密钥
- 复制竞品代码、图片、文案、商标、品牌资产
- 把逆向结论用于伪造身份、欺诈、侵权

如果用户要求上述内容，停止并说明只能做公开行为分析。

### 可选：rea skill

需要更深的功能/实现逆向时，若环境提供 `rea` skill 且用户授权，可加载它补充页面结构、交互与实现线索。先检查 skill 是否可用：

- 可用：按其流程执行，结论仍需标注证据来源。
- 不可用：回退到公开行为分析，不伪造逆向结果。
- 无论是否使用 `rea`，都禁止绕过登录/付费/DRM 或抓取非公开数据。

## 流程

### 第 1 步：建立证据包

在 `artifacts/01-feature-spec/evidence/` 下按「页面/流程」命名保存：

- 商店页截图、版本号、更新日期
- 首次启动、引导、登录、核心任务、付费、设置
- 空态、加载态、错误态、无网络、权限拒绝
- 页面结构导出（Android 可用 `adb shell uiautomator dump`，仅限自有/授权设备）
- 录屏或关键帧截图

Android 取证示例（仅限授权设备）：

```bash
adb shell uiautomator dump /sdcard/window.xml
adb pull /sdcard/window.xml artifacts/01-feature-spec/evidence/
adb exec-out screencap -p > artifacts/01-feature-spec/evidence/home.png
```

iOS 模拟器截图示例：

```bash
xcrun simctl io booted screenshot artifacts/01-feature-spec/evidence/home.png
```

真机 iOS 没有稳定的公开 UI dump 命令；使用 XCUITest、Appium 或手工截图，不要伪造结构数据。

### 第 2 步：页面级盘点

建立 `screens.md`，逐项记录：

| 字段 | 内容 |
| --- | --- |
| 页面 ID | SCR-001 |
| 页面名称 | 首页 |
| 入口 | 启动、Tab、推送、深链 |
| 关键组件 | 搜索、卡片、筛选、底部导航 |
| 状态 | 加载/成功/空/错误/离线/无权限 |
| 跳转 | 目标页面 ID |
| 证据 | evidence 文件名 |

检查所有入口：启动页、引导、登录/注册、每个 Tab、二级页、设置、消息、搜索、个人中心、付费页、客服/帮助、系统分享、推送落地页、深链落地页。

### 第 3 步：功能级盘点

建立 `feature-inventory.md`，主表列：

| 字段 | 说明 |
| --- | --- |
| 功能 ID | F-001 |
| 模块 | 账号 / 内容 / 交易 / 设置 |
| 功能名 | 用用户语言，不用实现语言 |
| 用户目标 | 用户想完成什么 |
| 入口 | 页面 ID + 控件 |
| 前置条件 | 登录、权限、数据、网络 |
| 主路径 | 编号步骤 |
| 分支路径 | 取消、返回、重复提交、失败重试 |
| 结果 | 成功态、失败态、副作用 |
| 权限 | 相机、相册、通知、定位、通讯录等 |
| 数据 | 读取/写入的字段、是否敏感 |
| 业务规则 | 限额、频率、排序、过期、风控 |
| 优先级 | P0 / P1 / P2 |
| 证据 | 截图/录屏/页面结构 |

优先级定义：

- **P0**：没有它产品无法完成核心闭环（发现、核心任务、数据保存）；**阶段 3 由 5 图最终锁定**。
- **P1**：明显影响体验或留存，但可延后一版
- **P2**：运营、边缘、低频、纯装饰

注意：这里标 P0 只是候选；5 图放不下的功能在 G3 降为 P1/P2。

### 第 4 步：流程建模

在 `flows.md` 用 Mermaid 至少画目标 App 实际存在的流程：

1. 首次启动 → 首页（有引导/登录则画）
2. 核心任务完整闭环（含失败、取消、重试）
3. 设置/隐私/数据清理
4. 付费/订阅（仅当目标 App 有）
5. 推送/深链落地（仅当目标 App 有）

流程节点标注页面 ID、功能 ID、判断条件。没有的流程不要硬造。

### 第 5 步：业务规则与数据

在 `business-rules.md` 记录：

- 账号体系：游客、注册、第三方登录、换绑、注销
- 权限与角色：普通用户、会员、管理员
- 交易：价格、币种、订阅周期、试用、退款、恢复购买
- 内容：发布、审核、删除、举报、排序
- 限制：次数、字数、文件大小、频率、地理范围
- 隐私：收集哪些数据、何时请求权限、能否拒绝后使用
- 通知：触发条件、渠道、免打扰

区分「观察到的行为」与「推断的规则」。推断必须标「假设」。

### 第 6 步：术语表

在 `glossary.md` 统一中英文术语、产品内叫法、代码命名建议。后续 PRD、UI、测试都用同一套词，避免「作品/内容/帖子」混用。

### 第 7 步：知识库自检

- 入口覆盖：每个可见入口都能落到页面 ID 和功能 ID
- 状态覆盖：每个 P0 页面有加载/空/错误/离线说明
- 流程覆盖：核心闭环可从任意入口走到结果
- 规则覆盖：权限、限额、付费、注销都有记录
- 未知项：单独列出，不藏在正文里

## Codex Handoff Packet

阶段 1 结束时生成 `artifacts/01-feature-spec/codex-handoff.md`，让 Codex 直接执行阶段 2/3：

- spec topic、目标 App、平台/技术栈/市场
- 功能知识库路径与关键功能 ID
- L1 提示词：二创主题、竞品、PRD、P0 5 屏草案、mock
- L2 提示词：设计系统、5 图、P0 锁定、Stitch/fallback
- 约束：不复制竞品资产、不声称官方关联、不写实现代码
- 执行方式：默认暂停等待 Codex；用户同意时可用 `codex exec`

## 产出

```text
artifacts/01-feature-spec/
├── feature-inventory.md
├── screens.md
├── flows.md
├── business-rules.md
├── glossary.md
├── codex-handoff.md
└── evidence/
```

每个文件头部写：

```markdown
> 版本: v0.1
> 日期: YYYY-MM-DD
> 作者: <Agent/人>
> 来源: <App 版本、设备、商店链接>
> 状态: draft | approved
```

## G1 门禁

- [ ] 所有可见入口映射到页面 ID 和功能 ID
- [ ] 每个 P0 功能有主路径、异常路径、空/错/加载态
- [ ] 至少 5 条关键流程有 Mermaid 图
- [ ] 权限、数据、业务规则已记录
- [ ] 术语表统一，PRD 可直接复用
- [ ] 未知项显式列出，没有用猜测填充
- [ ] 证据文件可追溯
- [ ] 单端证据即可通过；另一平台缺失不阻塞
- [ ] P0 为候选，等待阶段 3 由 5 图锁定
- [ ] `codex-handoff.md` 已生成

## 常见错误

- 只写页面不写功能：导致 PRD 无法验收
- 只写正常路径：测试阶段才发现空态/错误态没设计
- 把实现细节当业务规则：例如「用 Redis 缓存」不是用户可观察规则
- 混用竞品术语：后续设计和开发对不上
- 用截图代替结构化清单：无法检索、无法追溯
- 分析范围失控：先定 P0 闭环，再扩展，不要一次吞下整个 App
- 因缺少另一平台链接而停住：单端即可，另一平台可选后补
- 把 P0 当最终范围：5 图放不下时要降级
- 需要更深逆向却不用 `rea`，只凭截图猜实现
